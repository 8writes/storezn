### F-01 — Rate limiting collapses to one global bucket unless `TRUST_PROXY_HEADERS=true`
**Severity: High · Confidence: Confirmed in code; production impact is a Hypothesis pending one env check**

- `lib/rateLimit.js:15-26` — `getClientIp()` returns the literal string `"unknown"` unless `process.env.TRUST_PROXY_HEADERS === "true"`.
- `lib/rateLimit.js:28-31` — for an unauthenticated caller, `identityFor()` returns that IP, so the bucket key is `"<key>:unknown"` for **every** anonymous client.
- `TRUST_PROXY_HEADERS` appears nowhere except the three read sites (`lib/rateLimit.js:19`, `lib/requestUrl.js:25,29`) and is **not present in `.env`**.

Impact — every anonymous limiter becomes a platform-wide shared counter, which inverts its purpose from "throttle the attacker" to "let the attacker lock out everyone":

| Site | Limit | Effect when IP is `"unknown"` |
|---|---|---|
| `auth/login/route.js:73` | 40/min | 40 logins/min for the **whole platform** |
| `storefront/checkout/route.js:121` | 10/min | 10 checkouts/min platform-wide — a trivial revenue DoS |
| `auth/signup/route.js:23` | 5/min | 5 customer signups/min platform-wide |
| `vendor/signup/route.js:21` | 5/min | 5 vendor signups/min platform-wide |
| `auth/forgot-password/route.js:12` | 5/min | 5/min platform-wide |
| `storefront/invoices/lookup/route.js:22` | 10/min per store | per-store, but per-*store* not per-attacker |
| `storefront/invoices/[shareToken]/route.js:61` | 10/min | 10 invoice payments/min platform-wide |

Per-account limiters are unaffected (`login:email` keys on the email; `upload-file`/`review-image` key on `user.id`).

**To verify:** on the production host, `pm2 env <id> | grep TRUST_PROXY_HEADERS` (or check the `.env` the app actually loads). Also confirm nginx/Caddy sets `X-Forwarded-For`.
**Fix:** set `TRUST_PROXY_HEADERS=true` in production (the reverse proxy is trusted and terminates TLS — `scripts/deploy.sh` shows a single-host pm2 deployment). Then harden `getClientIp` to take the *last* untrusted hop rather than the first `X-Forwarded-For` entry, which is client-spoofable. Consider failing startup in production when the variable is unset, so this cannot regress silently.

### F-02 — A customer of store A can shop and check out on store B
**Severity: Medium · Confidence: Confirmed**

Nothing binds an authenticated `customer` to the store whose host the request arrived on:

- `app/api/v1/storefront/cart/route.js:46` — `resolveCart({ storeId: store.id, userId: user?.id, ... })`; `user` comes from `getUser(req)`, which is host-agnostic.
- `app/api/v1/storefront/checkout/route.js:149` — same call, then `checkoutAttempts.userId = user.id` (`:278`).
- `app/api/v1/storefront/reviews/upload/route.js:24` — checks `user.role === "customer"` only.

`customers` is deliberately store-scoped (`lib/db/schema.js:604-647`, unique on `(storeId, email)`), so this breaks that model rather than leaking another tenant's data.

**Repro:** sign up at `a.storezn.com`, keep the JWT, send it with `Host: b.storezn.com` to `POST /api/v1/storefront/cart`, then `POST /api/v1/storefront/checkout`.
**Impact:** (1) the resulting order's `userId` points at a customer row belonging to store A, so store B's `/vendor/customers` list (which filters `customers.storeId = B`) omits a real buyer and `customers/[customerId]` 404s for them — broken vendor CRM data; (2) store A's customers can burn store B's storage quota through the review-image upload.
**Fix:** in every storefront route that accepts a customer token, reject when `user.role === "customer" && user.storeId !== store.id`. A shared helper alongside `resolveStoreByHost` is the natural home.

### F-03 — `finalizePaidCheckoutAttempt` reports `created: true` for a losing concurrent caller → duplicate confirmation emails and pushes
**Severity: Medium · Confidence: Confirmed**

`lib/checkoutAttempts.js:207` returns `created: !!createdOrder`. But `createdOrder` is also populated on the two *loser* paths, where the order already existed and this call created nothing:

- `:90-93` — the locked attempt already has an `orderId`.
- `:130-135` — the status claim matched zero rows; the existing order is loaded instead.

Only the outermost early return (`:67-73`) sets `created: false` correctly.

Three callers branch on this flag to decide whether to notify:
- `app/api/v1/webhooks/paystack/route.js:318` — `if (!finalized?.created || !finalized.order) return;`
- `app/api/v1/storefront/orders/[orderNumber]/route.js:91` — `if (finalized.created) await sendOnlineOrderNotifications(...)`
- `lib/failStaleTransactions.js:48-51` — same.

**Repro:** deliver the same `charge.success` twice concurrently (Paystack retries on any non-2xx), or have the buyer load the return URL while the webhook is in flight. Both deliveries return `created: true`; the buyer gets two order-confirmation emails and the vendor two "New order" pushes.
**Fix:** track creation explicitly — set a `didCreate = true` flag only on the branch that performs the `insert(orders)` at `:139`, and return that instead of `!!createdOrder`.

### F-04 — Invoice payment references (`INV-…`) do not match the shared Paystack router's prefix convention
**Severity: Medium · Confidence: Confirmed (both sides read)**

The production webhook is registered on `website-ozmictech`, which forwards by reference prefix:

- `website-ozmictech/lib/paystack.js:40-41` — `const [prefix] = reference.split("-"); if (routeTable[prefix]) return routeTable[prefix];`, where the table is built from `PAYSTACK_ROUTE_<PREFIX>` env vars (`:22-24`).
- Storezn order refs are `STOREZN-ORD-…` (`checkout/route.js:230`) → prefix `STOREZN`. ✔
- Storezn subscription refs are `STOREZNSUB-…` (`subscribe/route.js:65`) → prefix `STOREZNSUB`. ✔
- **Storezn invoice payment refs are `INV-<invoiceNumber>-<hex>`** (`storefront/invoices/[shareToken]/route.js:78`) → prefix **`INV`**, which the routing comment never mentions and which needs an otherwise-undocumented `PAYSTACK_ROUTE_INV` entry. Without it `resolveTargetUrl` returns `null` and the `charge.success` is never forwarded.

**Mitigated, not fatal:** `app/api/cron/invoice-maintenance/route.js:17-30` polls pending invoice payments past `authorizationExpiresAt` and reconciles them via `verifyTransaction`. With a 30-minute authorization TTL (`[shareToken]/route.js:145`) and the cron at `*/5` (`scripts/install-cron.sh`), a paid invoice is confirmed **30–35 minutes late** instead of instantly — during which the customer sees "unpaid" after paying, and reminder emails can still go out.
**To verify:** check whether `PAYSTACK_ROUTE_INV` is set in `website-ozmictech`'s production env.
**Fix:** prefix invoice references `STOREZN-INV-…` so they route through the existing `PAYSTACK_ROUTE_STOREZN` entry (the webhook already dispatches invoice payments by looking the reference up in `invoice_payments`, `webhooks/paystack/route.js:246`, so no dispatch change is needed) — or add `PAYSTACK_ROUTE_INV` and document it. The prefix convention deserves a test.

### F-05 — Vendor signup lacks the abuse guards customer signup has
**Severity: Medium · Confidence: Confirmed**

`app/api/v1/auth/signup/route.js` (customer) implements four guards. `app/api/v1/vendor/signup/route.js` implements only the first two:

| Guard | Customer | Vendor |
|---|---|---|
| Banned-device check | `:31` | `:27` ✔ |
| Block-list check | `:51-59` | `:44-55` ✔ |
| Per-device signup flood → auto-ban | `:64-74` | **absent** |
| Per-IP signup flood (soft cap 8) | `:80-89` | **absent** |
| `maybeAutoBanFromAbuse` on block-list hit | `:57` | **absent** |
| `logAbuseEvent` on block-list hit | `:56` | **absent** |

Each vendor signup creates a `users` row + a `stores` row + a `branches` row (`:64-93`), so this is the more expensive path to farm, yet it is the less defended one. Only the 5/min rate limit stands in the way — and per F-01 that is currently a single global bucket.

**Fix:** extract the customer route's guards 3–5 into a shared helper in `lib/deviceBan.js` and call it from both signup routes, counting against `users` (`role = 'vendor'`) rather than `customers`.

### F-06 — Vendor email uniqueness is not normalised; no reserved-slug list
**Severity: Low · Confidence: Confirmed**

1. **Email.** `customers` has a `normalizedEmail` column with a partial unique index (`lib/db/schema.js:611,641-644`) and signup checks both forms (`auth/signup/route.js:91-96`). `users` has no equivalent: `vendor/signup/route.js:57` checks only `eq(users.email, vendor.email)`. `signupEmail` (`lib/validate.js:16-23`) blocks `+tags`, but **not** Gmail dot aliases — so `foo.bar@gmail.com` and `foobar@gmail.com` create two vendor accounts from one mailbox.
2. **Slug.** `vendorSignupSchema` (`lib/validate.js:76-84`) allows any `[a-z0-9]+`. There is no reserved-slug list anywhere in the repo (grepped). A vendor can claim `www`, `api`, `mail`, `admin`, `app`. `www` is the concrete bug: `proxy.js:41` and `lib/resolveStore.js:32` both treat `www.<rootDomain>` as the platform host, so a store with slug `www` is created successfully and is then permanently unreachable.
3. **Race.** Slug and email are pre-checked then inserted (`:39-60`, `:87`) with no `23505` handler, unlike customer signup (`auth/signup/route.js:117-122`) — concurrent duplicates surface as a 500 instead of a 409.

**Fix:** add `normalized_email` to `users` with a unique index and check it at vendor signup; add a reserved-slug deny list to `vendorSignupSchema`; wrap the insert in a `23505` handler.

### F-07 — Store-active check fails open when the store row is missing
**Severity: Low · Confidence: Confirmed**

`lib/auth.js:56-57` (staff), `:64-65` (customer), `:79-82` (legacy) all use `if (store && !store.isActive) return null;`. A missing store row (hard-deleted, or an FK left dangling) falls through and the token keeps working. `app/api/v1/auth/login/route.js:121` has the identical shape.

**Fix:** treat a missing store as not-active (`if (!store || !store.isActive) return null;`). Low impact today because `stores` is rarely hard-deleted — and F-20 shows that deletion currently fails anyway.

### F-08 — POS staff can settle a sale at an arbitrary price by claiming an offline replay
**Severity: High · Confidence: Confirmed**

`lib/pos.js:44-46` states the policy: *"A staff member cannot deliberately alter a price or discount."* The implementation does not enforce it.

1. `app/api/v1/vendor/stores/[storeId]/pos/sales/route.js:91-92` computes the gate:
   ```js
   const wantsPriceChange =
     data.items.some((i) => i.unitPrice != null || (i.lineDiscount || 0) > 0) || (data.discountAmount || 0) > 0;
   ```
   It inspects `unitPrice`, `lineDiscount` and `discountAmount` — but **not `capturedLineTotal`**.
2. `:55` — `const isOfflineReplay = data.offlineReplay === true || isDelayedSale;` is **client-controlled** (`offlineReplay` is a plain boolean in `posSaleSchema`, `lib/validate.js:743`).
3. `:144-149` — when `isOfflineReplay` is true, `capturedLineTotal` (a bare `z.coerce.number().min(0)`, `lib/validate.js:712`) *replaces* the catalogue line total:
   ```js
   const capturedLineKobo = isOfflineReplay && item.capturedLineTotal != null ? toKobo(item.capturedLineTotal) : null;
   const baseLineKobo = capturedLineKobo != null ? capturedLineKobo : ...
   ```
4. `posPriceAdjustmentPolicy` (`lib/pos.js:47-52`) therefore returns `blocked: false`, and the sale settles at the attacker's price with only `reviewRequired` set.

**Repro** (as a `staff` account on an Enterprise store with an open shift):
```
POST /api/v1/vendor/stores/<storeId>/pos/sales
{ "sessionId": "<open session>", "idempotencyKey": "<16 chars>",
  "offlineReplay": true, "soldAt": "<ISO, ~2 min ago, inside the shift>",
  "items": [{ "productId": "<₦100,000 item>", "quantity": 1, "capturedLineTotal": 1 }],
  "tenders": [{ "method": "cash", "amount": 1 }] }
```
Settles a ₦100,000 item for ₦1. `soldAt` must be ≥ `session.openedAt` and within 7 days (`:67-79`).

**Second bypass in the same flag:** `:238` guards the drawer-cash check with `if (lockedSession.status === "open" && !isOfflineReplay)`. Setting `offlineReplay: true` also skips `INSUFFICIENT_DRAWER_CASH`, so a cashier can hand out cash change the drawer does not have.

**Mitigation that exists:** the sale is flagged for owner review (`flaggedAt`, `:453`) and logged to `store_activity_logs` with the variance (`:394-406`). It is detectable after the fact, not prevented.

**Fix:** (a) include `capturedLineTotal` in `wantsPriceChange` whenever it differs from the catalogue line total and the caller is not an owner; (b) do not let the client assert `offlineReplay` — derive it solely from `soldAt` age (`isDelayedSale`), or require a server-verifiable marker of the offline queue; (c) apply the drawer-cash check to any sale settling into an open session.

### F-09 — A password reset does not invalidate existing sessions
**Severity: Medium · Confidence: Confirmed**

`app/api/v1/auth/reset-password/route.js:38-42` updates `passwordHash` and marks the token used. Nothing else.

JWTs are stateless, signed with a 30-day expiry (`auth/login/route.js:131,156`) and `lib/auth.js:28` verifies only signature + expiry. There is no `passwordChangedAt`, token version, or session table in `lib/db/schema.js`. So after a compromise, changing the password does **not** evict the attacker — their token stays valid for up to 30 days.

Related, same file: reset-password does not check `isBanned` or `deletedAt` before resetting.

**Fix:** add `passwordChangedAt` (and/or `tokenVersion`) to `users`/`staff`/`customers`, stamp it on reset, put `iat`/version in the JWT, and reject stale tokens in `getUser`. Also delete that account's other outstanding `reset` tokens on a successful reset.

### F-10 — Email links default to `http://` and bypass the deliberate forwarded-header hardening
**Severity: Low · Confidence: Confirmed**

`lib/requestUrl.js:21-32` deliberately refuses to trust `x-forwarded-host`/`x-forwarded-proto` unless `TRUST_PROXY_HEADERS=true`, with an explicit comment saying why, and defaults to `https` for any non-loopback host (`:14-19`).

Three security-email paths ignore that helper and read the headers raw, defaulting to **`http`**:
- `lib/emailVerification.js:29-31`
- `app/api/v1/auth/forgot-password/route.js:71-72`
- `app/api/v1/vendor/stores/[storeId]/staff/route.js:143-145`

**Not a host-header takeover** — I checked: `forgot-password:31-53` only finds an account when the host is either the platform root (`isPlatformHost`) or resolves to a real store, so an attacker-supplied `Host` yields no email. The residual issue is that if the reverse proxy does not set `x-forwarded-proto`, reset/verify/invite links are emitted as plaintext `http://` URLs carrying a valid one-hour reset token.
**Fix:** use `buildRequestUrl`/`getPublicAppOrigin` from `lib/requestUrl.js` in all three places.

### F-11 — `findSubAccount` pages only the first 100 sub-accounts
**Severity: Medium · Confidence: Confirmed**

`lib/paystack.js:84` — `fetch(\`${BASE_URL}/subaccount?perPage=100\`)`, with no pagination loop. `ensureSubAccount` relies on this for idempotency (its own comment at `:110-112` explains Paystack happily creates duplicates).

Once the platform passes 100 sub-accounts, a re-link silently creates a **second** Paystack sub-account for the same bank account, and `stores.subAccountCode` is repointed at it — splitting one vendor's payout history across two sub-accounts and breaking `listSettlements` reconciliation (`lib/settlementSync.js`).
Reduced likelihood because `payout-account/route.js:50-52` locks the account after first link (changes go through a super-admin unlock), but the failure is silent and money-adjacent.
**Fix:** paginate until `meta.next`/an empty page, or key the lookup on a stored mapping instead of listing.

### F-12 — POS sale accepts a client-supplied `orderNumber`
**Severity: Low · Confidence: Confirmed**

`pos/sales/route.js:225` — `let orderNumber = data.orderNumber || generateOrderNumber();`. `posSaleSchema` (`lib/validate.js:737`) constrains the shape to `/^ORD-[A-Z0-9]{6,10}$/`, and `orders.orderNumber` is globally unique with a regenerate-and-retry on collision (`:474-476`), so the blast radius is small. But a client can still deliberately squat a specific order number, or provoke a collision against another store's order number to probe existence.
**Fix:** treat the client value as a hint only — verify it is unused *within the store* and otherwise ignore it silently.

### F-13 — Subscription charges are trusted without `verifyTransaction` or an amount check
**Severity: Low · Confidence: Confirmed**

Order payments are double-checked: signature, then `verifyTransaction`, then an amount comparison (`webhooks/paystack/route.js:288-305`). Subscription charges are not — `handleSubscriptionCharge` (`:41-62`) reads `event.data.metadata.storeId` and `event.data.amount` straight from the payload and grants `plan: "plus"` for 31 days, with only `recordSubscriptionTransaction`'s unique reference as an idempotency gate.

The signature check makes forgery impractical, and the amount is server-set at initialize time, so this is defence-in-depth rather than an open hole. It does mean a charge that is later reversed still grants a paid month.
**Fix:** call `verifyTransaction` and compare against the expected plan price, matching the order path.

### F-15 — Review-image upload skips the magic-byte check that the vendor upload route performs
**Severity: Medium · Confidence: Confirmed**

### F-21 — Vendor deletion never removes any storage files (`isOwnedUploadUrl` called without a user id)
**Severity: Medium · Confidence: Confirmed**

`lib/deleteVendor.js:107`:

[...new Set(storageUrls)].filter((url) => isOwnedUploadUrl(url)).map((url) => deletePublicFile(url)...)

The signature is `isOwnedUploadUrl(url, userId)` (`lib/storage/cloudinary.js:141`). ### F-22 — The two storage providers implement `isOwnedUploadUrl` with different semantics
**Severity: Low (latent) · Confidence: Confirmed**

### F-23 — Push subscribe allows an arbitrary endpoint URL → authenticated blind SSRF
**Severity: Medium · Confidence: Confirmed**

`pushSubscribeSchema` (`lib/validate.js:803-809`) validates the endpoint as `z.string().trim().url()` — no scheme, host or allow-list restriction. `POST /api/v1/push/subscribe:40-46` stores it for any authenticated user. `lib/push.js:44-47` then makes a server-side `POST` to that exact URL via `webpush.sendNotification` whenever a notification fires for that principal.

**Repro:** as a vendor, subscribe with `{"endpoint":"http://127.0.0.1:3003/api/...","keys":{"p256dh":"x","auth":"y"}}`, then place an order in your own store — `sendPushToStore` (`push.js:88`) fires and the server POSTs to that internal URL. Also reachable: `http://169.254.169.254/…` (cloud metadata), any internal port.

The response body is not returned, so this is *blind*. There is a weak oracle: `push.js:51` prunes the row only on a 404/410 response, so endpoint reachability is partially observable.
**Fix:** restrict `endpoint` to `https:` on a known push-service host allow-list (FCM/Mozilla/WNS/Apple) — or at minimum reject non-`https`, private/loopback/link-local hosts, and resolve-then-check before sending.

### F-24 — Push subscribe reassigns an endpoint row without checking who owns it
**Severity: Low · Confidence: Confirmed**

`app/api/v1/push/subscribe/route.js:43-46` — `onConflictDoUpdate` on `endpoint`, overwriting `userId`/`staffId`/`customerId` with the caller's id and no check on the existing owner. The comment at `:22-25` says this is intentional for shared devices.

Consequence: any authenticated user who knows another user's endpoint URL can take the row over. They cannot read the victim's notifications (payloads would be encrypted to the attacker's keys but delivered to the victim's browser, which cannot decrypt them) — but the victim silently stops receiving notifications.
**Fix:** on conflict, only reassign when the row is unowned or already owned by the caller; otherwise delete and re-insert after verifying the subscription is genuinely stale.

### F-28 — The E2E database safety guard accepts the currently configured database
**Severity: Medium · Confidence: Confirmed**

`tests/e2e/helpers/db.mjs:6-22` refuses to run unless the database looks like a test database:
```js
const SAFE_DB_RE = /(test|temp|dev|local|e2e)/i;
const local = ["localhost", "127.0.0.1", "::1"].includes(url.hostname);
const safeName = SAFE_DB_RE.test(url.pathname) || SAFE_DB_RE.test(url.hostname);
if (process.env.E2E !== "1" || (!local && !safeName)) throw ...
```
Two independent weaknesses:
1. `local` is judged from the **hostname only**. The configured `DATABASE_URL` resolves to `127.0.0.1` / database `postgres` (verified without printing credentials), so the guard passes — even though a loopback address is exactly what a tunnel or connection proxy to a remote database looks like.
2. `SAFE_DB_RE` matches the substring `temp`, which would classify a branch named `storezn-temp` as a test database.

The helper performs 13 insert/update/delete operations. **This is why I did not run the E2E suite** (§4).
**Fix:** require an explicit opt-in that cannot be satisfied by accident — e.g. a dedicated `E2E_DATABASE_URL` plus a sentinel row the test database must contain — rather than pattern-matching the hostname.

### Behaviour changes worth knowing about

- A non-owner settling a queued sale whose price drifted more than 20% or
  ₦5,000 now gets a 403 and the owner has to complete it (F-08). Previously it
  settled silently and was flagged for review.
- A queued sale whose cash change exceeds the drawer's expected cash is now
  recorded and flagged for owner review (`drawerWentNegative`) rather than
  silently accepted. A LIVE sale in that position is still refused outright,
  as before - the difference is that a replay's change has already been handed
  over, so refusing the sync would lose the record without recovering the cash.

### Correction to an earlier draft of this log

An intermediate version of the F-08 fix gated captured offline pricing on the
sale being more than 90 seconds old (`isDelayedSale`) instead of on the replay
flag, and turned the drawer-cash check into a hard refusal for replays too.
Both were wrong, and the first was a real regression rather than the cosmetic
one first recorded here:

The POS sell screen computes the **tenders on the device from its cached line
prices**, and `validateTenders` requires them to match the server's total to
the kobo. Re-pricing a queued sale from the current catalogue therefore does
not produce a slightly different receipt - it makes the totals disagree and
**rejects a completed sale with "Payments don't add up to the total"**, cash
already in the drawer. A device whose cache went stale over a long offline
stretch hits this on its very next sale, and only when it reconnects quickly,
making it timing-dependent and hard to diagnose.

The 90-second gate also bought no security: `soldAt` is client-supplied, so an
attacker simply backdates it. The real control is
`offlineDriftWithinStaffAllowance`. Both behaviours are reverted to follow the
replay flag, with the bound doing the work, and
`tests/auditFixes.test.mjs` now guards against re-introducing either (negative
control verified for both).
- Changing your own password now rotates your token (F-09). Both profile pages
  adopt the new one; any other client calling `PATCH /api/v1/auth/me` with a
  password change should read `token` from the response.
- `GET /api/v1/super-admin/vendors/[id]/nin` is capped at 20 reveals per hour
  per account (F-25).

### F-14 follow-up: the 38 `react-hooks/set-state-in-effect` errors are now fixed

Deferred in the first pass, done as its own pass afterwards. Lint is now
**0 errors** (was 228): `262 problems → 33 problems`, and all 33 remaining are
`@next/next/no-img-element` warnings — a Next.js suggestion to use `next/image`,
which needs remote-image domains configured for Cloudinary and is a separate
decision, not a defect.

The 38 errors were three patterns, each fixed the same way everywhere so the
loading behaviour is consistent across every page:

**1. `setLoading(true)` at the top of a fetch effect** (most of them). The fetch
moved inline into the effect with a `let alive = true` guard and a cleanup that
flips it. `loading` now starts `true` and is only ever *cleared* when a fetch
settles; it is switched back *on* by whichever interaction asks for fresh data.
Mutations that used to call `load()` bump a `refreshKey` the effect depends on.

This also fixes a real bug class that was there before: responses are now
dropped if their inputs changed while in flight, so a slow page-1 reply can no
longer land on top of page 2.

**2. `useEffect(() => setPage(1), [q])`** — resetting pagination when a filter
changes. Moved into the handler that causes it (`handleSearch`, `handleStatus`,
`handlePageChange`, …), which is where React wants it. Where the trigger is the
shared store switcher rather than a handler on the page (`vendor/orders`,
`vendor/customers`), the page number is instead *derived* — it only counts for
the store it was chosen on, so switching stores falls back to page 1 with no
effect involved.

**3. Copying external or prop state into state on mount.**
- `ThemeToggle` and the dashboard sidebar collapse now read their
  localStorage-backed values through `useSyncExternalStore`
  (`subscribeToTheme` / `subscribeToNavCollapsed`, the latter in a new
  `lib/navCollapse.js`). Both previously rendered the default for one frame
  before snapping to the stored value.
- Both profile pages derive the edit form from `user` instead of copying it in
  an effect. That also removes a latent bug: a background refresh of `user`
  used to overwrite whatever someone was in the middle of typing.
- `SearchInput` adjusts to a changed `value` prop during render against the
  previous value (React's documented pattern) instead of in an effect.
- Detail pages (`vendor/customers/[id]`, `vendor/shipping`) tag loaded data
  with the key it belongs to and derive `loading` from that, so navigating
  between records shows the skeleton instead of the previous record's data.
- `vendor/pos/sessions` (an append-style "load more" feed) keeps the whole feed
  in one value tagged with its store, so a store switch reads as an empty
  loading feed with nothing resetting it.

Verification: `npm run lint` → 0 errors; `npm run test:unit` → 97/97;
`npm run test:pos` → 8/8; every changed file passes `node --check`; the changed
and new `lib/` modules all import cleanly. **The build is still yours to run.**

### A real bug this check found: `order_items.customer_fields`

The first run showed one column in the database that the code did not
declare: `order_items.customer_fields`, added by
`INVOICE-FLOW-MIGRATION.sql` as `jsonb NOT NULL DEFAULT '{}'`.

That is not harmless drift. `finalizePaidCheckoutAttempt`
(`lib/checkoutAttempts.js:192`) has always passed `customerFields` when
inserting order items, but because the column was never declared in
`lib/db/schema.js`, **drizzle silently dropped the key** - no error, the
insert succeeded, and the row kept the `'{}'` default.

Effect: every online order stored an empty object, so the buyer's answers to
vendor-defined product fields (measurements, engraving text, event details)
never appeared on either order-detail view, both of which render them
through `components/ui/OrderItemModal.js`. `invoiceItems.customerFields`
was declared, so the invoice journey worked - only the checkout journey lost
them.

Fixed by declaring the column on `orderItems`. No migration needed; the
column already existed. Guarded by two tests in `tests/auditFixes.test.mjs`
asserting `customer_fields` is declared on all three rows that snapshot it
(cart, order, invoice).

Answers for orders placed before this fix are recoverable from
`checkout_attempts.items`, which snapshots them as JSONB and was never
affected.
